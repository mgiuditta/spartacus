## P4 [non supportato] — sezione 3.5 (paragrafo dopo il punto 7) e sezione 9, trappola 8
- Testo nel capitolo: "Ne consegue che una feature registrata dopo `INIT` riceve all'`UPDATE` lo slice trasferito come stato precedente (non `undefined`), quindi il suo `initialState` non viene applicato a quello slice." e (trappola 8) "una feature registrata dopo riceve lo slice trasferito come stato precedente all'`UPDATE` … Lo slice deve quindi essere già \"completo\"."
- Problema: la conclusione non segue dal codice citato. Le chiavi extra fuse all'`INIT` (gli slice di feature non ancora registrate) restano nello state root solo finché **nessun** reducer registrato cambia riferimento. Al primo cambiamento, di qualunque feature registrata e per qualunque azione (anche un `UPDATE` di un'altra feature), `combineReducers` restituisce un oggetto nuovo con le sole chiavi registrate, e lo slice trasferito della feature non ancora registrata si perde. Se una feature tardiva riceva lo slice trasferito o `undefined` (e quindi il proprio `initialState`) dipende dunque dalla sequenza di azioni tra `INIT` e la sua registrazione, non solo dall'ordine DI. Lo stesso paragrafo del capitolo riporta la regola ("altrimenti un nuovo oggetto con le sole chiavi registrate") ma non ne trae questa conseguenza. Anche "lo slice deve essere già completo" va attenuato: se la feature usa una mappa di reducer (`combineReducers` di feature), le sotto-chiavi assenti dallo slice ricevono comunque il default del rispettivo sotto-reducer.
- Correzione: "Una feature registrata dopo `INIT` riceve lo slice trasferito come stato precedente **solo se** nessun reducer registrato ha cambiato riferimento tra `INIT` e il suo `UPDATE`; altrimenti `combineReducers` ha già scartato le chiavi non registrate e la feature parte dal proprio `initialState`. ⚠️ DA VERIFICARE a runtime quali feature siano registrate all'`INIT` e quali azioni le precedano." — `deps:ngrx-store-21.0.1/package/fesm2022/ngrx-store.mjs:L329-L341` (`const nextState = {}; for (...) { ... nextState[key] = nextStateForKey; hasChanged = hasChanged || nextStateForKey !== previousStateForKey; } return hasChanged ? nextState : state;`), `core-libs/core/src/state/reducers/transfer-state.reducer.ts:L89-L93` (`state = deepMerge({}, state, transferredStateSlice); } return state; } return reducer(state, action);`).

## P5 [impreciso] — sezione 3.9
- Testo nel capitolo: "Sul server l'interceptor salva in `TransferState` le risposte riuscite cacheabili (GET/HEAD, senza credenziali/auth/cookie, senza `Cache-Control` no-store/private, senza `Set-Cookie`)"
- Problema: le direttive `Cache-Control` escluse sono tre: `no-store`, `private` e **`no-cache`**. Il controllo vale sia per gli header della richiesta sia per quelli della risposta, e sono escluse anche le richieste con `cache: 'no-cache' | 'no-store'` della Fetch API e quelle scartate dal `filter`. Le `POST` sono cacheabili con `includePostRequests` o con l'opzione a livello di richiesta, quindi "GET/HEAD" descrive solo il default.
