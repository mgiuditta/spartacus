Seleziona poi le voci la cui `version` soddisfa il range `>from <=to` (`deps:devkit/angular-cli-21.2.23/package/src/commands/update/utilities/migration.js:L107-L118`: `const migrationRange = new semver.Range('>' + ... from ... + ' <=' + to.split('-')[0]);` … `if (semver.satisfies(description.version, migrationRange, { includePrerelease: true }))`). Le esegue in ordine di versione e poi di **nome** (`deps:devkit/angular-cli-21.2.23/package/src/commands/update/utilities/migration.js:L127-L127`: `requiredMigrations.sort((a, b) => semver.compare(a.version, b.version) || a.name.localeCompare(b.name));`).
  - Conseguenza da aggiungere in §3.9 punto 2: il prefisso `00-`…`09-` delle chiavi è ciò che fissa l'ordine d'esecuzione dentro una stessa versione.
  - Conseguenza per §3.11 e per la domanda 7: la living migration gira in ogni `ng update` che passa da una versione `< 221121.22.0` a una `>= 221121.22.0`, perché a ogni release la sua `version` viene allineata al pacchetto. Non gira se `from` è già pari a quella versione.
- **§6, riga `ng-add.save`.** La CLI legge `manifest['ng-add']?.save` (`deps:devkit/angular-cli-21.2.23/package/src/commands/add/cli.js:L426-L426`) e installa come dev dependency se vale `'devDependencies'` (`deps:devkit/angular-cli-21.2.23/package/src/commands/add/cli.js:L473-L473`).
- **§9 trappola 8 ("se il devkit li deduplica").** Non li deduplica. `TaskScheduler.schedule` accoda ogni task con un id nuovo (`deps:devkit/angular-devkit-schematics-21.2.23/package/src/engine/engine.js:L117-L130`), ed `executePostTasks` li esegue tutti in sequenza (`deps:devkit/angular-devkit-schematics-21.2.23/package/src/engine/engine.js:L283-L297`).
